\subsection{Оценка решения}

В данном разделе будет произведена качественная и количественная оценка решения.

\subsubsection{Пространственная и временная сложность} \label{sec:complexity}

Рассмотрим алгоритмическую сложность \cite{clrs_algorithms} решения. Размеры трассы и количество итераций при проходе по ней пропорциональны количеству инструкций в трассе $N$. Заметим, что $N \sim |V|$ -- множество $V$ состоит из инструкций трассы и фиксированного количества псевдоинструкций.

Рассмотрим временную и пространственную сложность стадий обработки трассы:

\begin{itemize}
    \item Генерация карты перемещений

    Временная сложность -- $O(N)$ (полный проход по трассе).
    Пространственная сложность -- $O(N)$ (агрегация данных с записей трассы).

    \item Сбор ГПД

    Временная сложность -- $O(N)$ (полный проход по трассе).
    Пространственная сложность -- $O(N + K)$, где $K = |E|$ -- количество ребер ГПД.

    \item Генерация модификаций трассы

    На данной стадии производятся два обхода ГПД: построение обратных путей и прямой обход. При этом ни одно ребро не обходится дважды, так как обработанные ребра отмечаются маркерами. Временная сложность обходов графа -- $O(N + K)$. Также в конце производится симуляционный проход по модифицированной трассе, временная сложность -- $O(N)$.

    Результирующая временная сложность -- $O(N + K)$.

    На данной стадии генерируются модификации трассы, количество которых пропорционально количеству инструкций и количеству ребер ГПД. Пространственная сложность -- $O(N + K)$.

    \item Модификация трассы

    Временная сложность -- $O(N)$ (полный проход по трассе).
    Пространственная сложность -- $O(1)$.
\end{itemize}

Заметим, что количество ребер, входящих в любую вершину, ограничено константой (ограничение системы команд платформы). Значит, выполняется асимптотическая оценка: $K = O(N)$. Таким образом, пространственная и временная сложность обработки трассы $O(N + K) = O(N)$.

\subsubsection{Оценка репрезентативности трасс}

Как было описано в разделе \ref{sec:representativeness}, компенсируемые записи могут существенно ухудшать репрезентативность трасс. При этом единожды произошедшая при симуляции инструкции трассы компенсация приводит к добавлению компенсационного кода для \textbf{всех} инструкций трассы, отвечающих той же инструкции приложения. Рассмотрим различные модификации трассы и их влияние на репрезентативность:

\begin{itemize}
    \item Замена адреса для операции с памятью -- не влияет на репрезентативность, так как не требует компенсации при дальнейшей обработке выходной трассы.

    \item Замена значения для записи в память -- не требует компенсации (поток данных консистентен).

    \item Замена значения для чтения из памяти -- может влиять на репрезентативность в некоторых сценариях.

    При чтении значения, не соответствующего текущему образу памяти рассматриваемого потока, может потребоваться компенсация, аналогичная компенсации для внешней модификации памяти. Заметим, что если в оригинальной трассе уже присутствовала внешняя модификация памяти, репрезентативность существенно не изменится.

    \item Замена значения регистра в начальном состоянии -- не требует дополнительной компенсации.

    \item Замена значения для записи в регистр общего назначения -- не требует дополнительной компенсации.

    \item Добавление записи в регистр общего назначения -- требует компенсации и будет снижать репрезентативность.
\end{itemize}

Для оценки влияния модификаций на репрезентативность трасс будем использовать кумулятивную метрику $N_{comp}$ -- количество инструкций трассы, при симуляции которых будет исполнен компенсационный код, появившийся из-за произведенных над трассой модификаций (далее -- компенсируемые инструкции). Обозначим также $P_{comp} = \frac{N_{comp}}{N}$ -- долю компенсируемых инструкций в трассе. Данные метрики позволяют предварительно (без полноценного анализа выходных трасс на симуляторе) оценить качество произведенных модификаций и репрезентативность получаемых трасс.

\subsubsection{Профилировка решения по памяти} \label{sec:memory_profiling}

Для получения грубой оценки потребления памяти различными компонентами использовалась утилита heaptrack \cite{heaptrack_documentation}, позволяющая отследить объемы выделений памяти различными участками кода. Данные heaptrack для набора тестовых трасс показывают, что в коде библиотеки boost graph выделяется больше 90 процентов используемой памяти. Значит, большую часть потребляемой памяти занимает ГПД. При этом выполняется: $M_{\texttt{ГПД}} = O(N + K) = O(N)$, где $M_{\texttt{ГПД}}$ -- объем памяти, занимаемый графом.

\subsubsection{Тестовые запуски на целевых трассах} \label{sec:real_trace_tests}

В данном разделе будут представлены результаты тестовых запусков на целевых трассах заказчика. Трассы сгруппированы по целевым сценариям исполнения, для каждого сценария приведено до 10 трасс. Для тестов используется одна из исследуемых конфигураций системы памяти: с увеличенным размером страниц и резервированием дополнительных областей под данные ядра ОС. На этапе обработки трасс собирались следующие метрики:

\begin{itemize}
    \item $N$ -- общее количество инструкций трассы.
    \item $N_{comp}$ -- число компенсируемых инструкций.
    \item $P_{comp} = \frac{N_{comp}}{N}$ -- доля компенсируемых инструкций. Будем считать трассы с $P_{comp} \leq 0.01$ репрезентативными.
    \item $RSS_{max}$ -- максимальный объем резидентной памяти (resident set size) \cite{gnu_time_memory_resources,linux_proc_filesystem}, занятый при модификации трассы.
    \item $P_{RSS} = \frac{RSS_{max}}{N}$ -- объем резидентной памяти на инструкцию трассы.
    \item $T$ -- время обработки трассы.
    \item $V = \frac{N}{T}$ -- средняя скорость обработки (инструкций трассы в секунду).
\end{itemize}

После завершения обработки результирующие трассы были верифицированы с помощью функционального симулятора. Собранные метрики представлены в таблице \ref{tab:experimental_data} (приложение \ref{app:experimental_data}).

Общее количество тестовых трасс: $M = $ \textbf{272}, из них \textbf{264 (97\%)} успешно прошли обработку, \textbf{217 (80\%)} прошли верификацию. \textbf{132 (49\%)} трассы прошли верификацию и имеют $P_{comp} \leq 0.01$ -- данные трассы могут быть использованы для исследования производительности платформы.

Рассчитаем обобщающие показатели для $P_{comp}$, $P_{RSS}$ и $V$.

Для $P_{comp}$ приведено среднее арифметическое: доля компенсированных инструкций трассы характеризует качество выходной трассы, а подобное усреднение позволит оценить долю компенсаций в случайно выбранной трассе. При этом не учитываются размеры тестовых трасс, так как на долю компенсаций в первую очередь влияют особенности потоков данных и управления. Также приведена медиана, так как на ряде тестовых трасс данная метрика существенно выше, что может говорить о наличии большого количества еще не поддержанных краевых случаев.

\vspace{0.3cm}

$\displaystyle \overline{P_{comp}} = \frac{1}{M} \sum_{i} P_{comp_i} = \left( 2.50 \pm 0.15 \right) \cdot 10^{-2} $

\vspace{0.3cm}

$ \displaystyle \operatorname{Med}\left( P_{comp} \right) = 9.97 \cdot 10^{-3} $

\vspace{0.3cm}

$P_{RSS}$ также усреднено с помощью среднего арифметического: потребление памяти линейно зависит от количества инструкций (остальные накладные расходы пренебрежимо малы). Значит, потребление памяти на одну инструкцию также будет в первую очередь зависеть от свойств потоков управления и данных (например, от количества ребер на одну инструкцию), но не от размеров трасс. Подобная оценка позволит оценить максимальное суммарное количество инструкций в наборе трасс, который можно обрабатывать одновременно в условиях ограниченной памяти.

\vspace{0.3cm}

$\displaystyle \overline{P_{RSS}} = \frac{1}{M} \sum_{i} P_{RSS_i} = \left( 0.443 \pm 0.002 \right) \frac{\texttt{Гб}}{10^6} $

\vspace{0.3cm}

Для $V$ приведено взвешенное гармоническое среднее, являющееся средней скоростью обработки всего массива тестовых трасс.

\vspace{0.3cm}

$\displaystyle \overline{V} = \frac{\displaystyle \sum_{i} N_i}{\displaystyle \sum_{i} T_i} = \left( 1.08 \pm 0.04 \right) \cdot 10^{5} \frac{1}{\texttt{С}}$
